## Mục tiêu

Cuối mốc:

- **DB không làm request treo vô hạn:** chờ khoá quá lâu, câu lệnh quá lâu, transaction bỏ dở đều bị Postgres cắt và trả lỗi rõ ràng (503 `SERVICE_UNAVAILABLE` + `Retry-After`) thay vì treo tới timeout của client (M3 bài học 5);
- **Rate limit** đúng cả khi chạy nhiều instance api: chặn dò mật khẩu (theo IP **và** theo email), spam đăng ký / mời / upload; trả 429 `RATE_LIMITED` + `Retry-After`;
- **Danh sách meeting có chi phí bị chặn** ở cả ca "thấy nhiều" lẫn "không thấy gì" (M6b bài học 9: ca rỗng 343 ms nếu chỉ viết lại), đo bằng benchmark 100k meeting trước / sau;
- **Quyền tối thiểu ở DB + RLS làm lớp phòng thủ thứ 2:** app không còn kết nối bằng superuser; Postgres tự chặn đọc / ghi chéo tổ chức kể cả khi một query trong code quên `org_id`.

## Ngoài phạm vi

- Presigned upload (đổi lớn luồng M5 đang ổn định), OpenTelemetry (cần hạ tầng xem trace), nâng Node 26 (chờ Node 26 lên LTS) — giữ trong lộ trình, làm ở mốc sau nếu muốn.
- RLS theo **từng người xem** (đưa `meetingVisibleTo` vào policy): điều kiện xem vẫn ở một chỗ trong code (04 §3); RLS ở mốc này chỉ giữ **ranh giới tổ chức**.
- WAF / chống DDoS tầng mạng — việc của reverse proxy / hạ tầng.

Quyết định nhỏ đã tự chốt, sửa được nếu bạn muốn:

- Header rate limit theo chuẩn IETF draft: `RateLimit-Limit`, `RateLimit-Remaining`, `RateLimit-Reset`; 429 có `Retry-After` (giây). Trùng tên với `@nestjs/throttler` thì dùng của thư viện.
- ~~Đếm theo cửa sổ cố định~~ → **sliding log** (đổi ở B2, xem bài học 4): ZSET thời điểm từng hit trong Redis — không còn "dồn ở mép cửa sổ" (tối đa 2× giới hạn với cửa sổ cố định), đổi lại bộ nhớ O(limit) mỗi khoá (giới hạn lớn nhất 300 → chấp nhận được).
- Redis sập → rate limit **cho qua** (fail-open, log lỗi): không để mất Redis làm sập cả đăng nhập. Hệ quả: lúc Redis sập không có rate limit.
- Benchmark đặt ở `scripts/bench/` (không chạy trong CI), dùng DB tạm tự tạo / tự xoá, in bảng số đo vào plan.
- Chi phí RLS (+1 round-trip mỗi lần lấy connection) **đo và ghi lại**, không đoán.

## Thay đổi thiết kế

- **03-database:** cột `meeting_shares.recorded_at` + index (Q4); các role + GRANT (Q5); bảng có RLS + policy + `app.org_id` (Q6); `lock_timeout` / `statement_timeout` / `idle_in_transaction_session_timeout` vào §7.
- **05-api:** 429 + header rate limit, giới hạn từng nhóm route (Q3); 503 + `Retry-After` khi DB bận (Q1).
- **07-conventions:** env mới (`DATABASE_LOCK_TIMEOUT_MS`, `DATABASE_STATEMENT_TIMEOUT_MS`, `DATABASE_IDLE_TX_TIMEOUT_MS`, `TRUST_PROXY_HOPS`, URL / mật khẩu role app + worker); mã lỗi 503 cho DB bận.
- **02-architecture:** ngữ cảnh tổ chức qua `AsyncLocalStorage` → `app.org_id` (Q6); api / worker / migrate dùng ba role khác nhau.
- **Dependency mới:** `@nestjs/throttler` (theo skill `add-dependency` ở B2).

## Điều sẽ học

- Timeout phía Postgres (`lock_timeout`, `statement_timeout`, `idle_in_transaction_session_timeout`) khác timeout phía client thế nào; lỗi nào nên trả 503 để client thử lại
- Rate limit phân tán: tính nguyên tử bằng Lua, cửa sổ cố định vs trượt, khoá theo nhiều chiều (IP, email, user), `trust proxy` và giả mạo `X-Forwarded-For`
- Đọc kế hoạch thực thi trên dữ liệu đủ lớn; đổi cách viết SQL để chi phí bị chặn; phi chuẩn hoá có kiểm soát (một cột chép + cập nhật cùng transaction)
- Quyền tối thiểu ở DB; RLS: `FORCE`, superuser / `BYPASSRLS`, `current_setting(…, true)`, ngữ cảnh theo connection trong pool và bẫy rò ngữ cảnh

## Điều học được / bẫy gặp phải

1. **Bật `idle_in_transaction_session_timeout` mà không xử lý thì tệ hơn không bật: tiến trình CHẾT.** `pg-pool` 3.14 gắn listener `'error'` cho client lúc RẢNH và GỠ nó trong `_acquireClient` khi cho mượn (gắn lại ở `_release`). Postgres cắt session đang được app mượn (giữa một transaction) → gửi `FATAL 25P03` → client phát `'error'` không ai nghe → **uncaught exception** (test tái hiện được trước khi sửa). Sửa: `pool.on('connect', client => client.on('error', …))` — listener cố định, chỉ ghi log; người đang mượn vẫn nhận lỗi ở câu lệnh kế tiếp, `release(err)` bỏ client hỏng, pool vẫn chạy. Đột biến bỏ listener → 2 uncaught exception.
2. **`lock_timeout` phải nhỏ hơn hẳn idle timeout — hai timeout bằng nhau chạy đua.** Lần chạy đầu đặt cả hai 300 ms: ca M3 (dùng `db` trong transaction có khoá) KHÔNG ra `55P03` mà ra lỗi mất kết nối. Lý do: trong lúc lệnh của connection B chờ khoá, transaction A (giữ khoá) cũng đang "idle in transaction" → Postgres giết A trước, khoá nhả, B chạy tiếp; lỗi nổ ra ở phía A. Production (3 s < 30 s) đúng, nhưng cấu hình sai thì Postgres giết nhầm bên. `createPgPool` từ chối khởi động nếu `lock ≥ idle`. Tương tự, đột biến bỏ `lock_timeout` vẫn "không treo" — nhưng nhờ idle timeout giết A, nên test phải kiểm ĐÚNG mã `55P03` chứ không chỉ "không treo".
3. **Timeout phía Postgres khác `connectionTimeoutMillis` của `pg`.** Cái sau chỉ giới hạn thời gian CHỜ LẤY connection từ pool (pool cạn); request đã có connection mà chờ khoá thì trước đây treo vô hạn. Ba timeout mới được `pg` gửi trong startup packet → áp cho MỌI câu lệnh, kể cả câu Drizzle sinh, không cần `SET` ở đâu. `55P03` / `57014` → 503 `SERVICE_UNAVAILABLE` + `Retry-After: 1` (e2e: khoá dòng tổ chức từ connection khác → `PATCH` org trả 503 sau ~3 s, nhả khoá → 200). 4 đột biến (bỏ `lock_timeout`, bỏ `statement_timeout`, bỏ listener, bỏ map 503) đều đỏ. Mẹo: `timeout` (GNU coreutils) không có trên macOS — lệnh đột biến bọc trong `timeout` trả exit 127 mà không chạy gì; phải nhìn số test đỏ, không chỉ exit code.
4. **Đọc code thư viện trước khi viết theo trí nhớ: storage mặc định của `@nestjs/throttler` 6.7 không còn là cửa sổ cố định.** Plan ghi "fixed window như storage mặc định"; đọc `throttler.service.js` thì thấy nó lưu hạn của TỪNG hit (`hitExpirations`) và lọc dần — sliding log. Hợp đồng `increment(key, ttl, limit, blockDuration)`: `ttl` / `blockDuration` tính **ms**, trả `timeToExpire` / `timeToBlockExpire` tính **giây**; đang bị chặn thì hit không được đếm, hết chặn đếm lại từ 0. `RedisThrottlerStorage` làm đúng như vậy trong MỘT Lua script: `PTTL` khoá chặn → `ZREMRANGEBYSCORE` hit cũ → `ZADD` → `ZCARD` → vượt thì `DEL` + `SET … PX`. Giờ lấy bằng `TIME` của Redis (các instance lệch đồng hồ vẫn chung một trục). `ThrottlerStorageRecord` không được export ở entry chính → suy kiểu từ `ThrottlerStorage['increment']` thay vì import sâu `dist/`.
5. **Vì sao phải Lua — chứng minh bằng đột biến.** Bản "lệnh rời" (`ZREMRANGEBYSCORE`, `ZADD`, `ZCARD` ba round-trip) với 50 request song song: ioredis xếp hàng lệnh theo thứ tự gửi → cả 50 `ZADD` chạy xong trước mọi `ZCARD` → ai cũng thấy 50 → **0** request được qua (thay vì 10). Không nguyên tử thì sai theo cả hai chiều (chặn oan hoặc lọt) tuỳ thứ tự xen kẽ. 3 đột biến (lệnh rời, mỗi instance một bộ đếm, không xoá lượt đếm khi chặn) đều đỏ. `defineCommand` của ioredis gửi `EVALSHA`, Redis mất script (restart) thì tự gửi lại `EVAL`. Hai khoá của một tracker bọc hash tag `{…}` để cùng slot nếu sau này dùng Redis Cluster.
6. **Test race chập chờn khi chạy cả bộ (lần 2, sau M10 bài học 4) — chưa rõ nguyên nhân, đã thêm chẩn đoán.** 1/4 lượt e2e đầy đủ đỏ ở `channel-owner-removal-race` ("GỠ TRƯỚC"): `waitForLockWaiters` 5 s không thấy transaction nào chờ khoá; chạy riêng file 4/4 xanh. Giả thuyết "cạn connection" bị loại bằng số đo: lấy mẫu `pg_stat_activity` của container test suốt một lượt đầy đủ → tối đa 42/100 connection, và cạn thật thì Postgres trả `53300` NGAY chứ không làm chờ 5 s. Không sửa theo đoán (M5 bài học 21); thay vào đó `waitForLockWaiters` hết giờ thì in trạng thái mọi backend của database (state, `wait_event`, thời gian trong transaction, câu query) — lần đỏ tới sẽ có dữ kiện. Kèm theo: lượt đỏ đó còn 3 **uncaught `57P01`** — teardown `DROP DATABASE … WITH (FORCE)` cắt connection mà test kẹt vẫn đang MƯỢN, đúng bẫy `pg-pool` của bài học 1 nhưng ở pool của test (`createTestDb`). Thêm listener cố định cho client (chỉ nuốt `57P01`) để uncaught không che lỗi thật.
7. **Plan tự mâu thuẫn — phát hiện khi viết test.** Q3 khoá đăng nhập theo (IP, email), nhưng test B3 đòi "đổi IP vẫn bị chặn": với khoá (IP, email), đổi IP là khoá mới. Chặn dò phân tán phải có thêm khoá **theo email** — nhưng khoá email chặt (5 / phút) thì kẻ xấu spam sai mật khẩu là khoá được tài khoản nạn nhân. Chốt 3 lớp: IP 30 / phút, (IP, email) 5 / phút (chặt), email 20 / giờ (lỏng). Hai lớp sau là hai throttler có tên chỉ bật trên route gắn `@CredentialThrottle()`; khoá trong Redis là sha256 nên email không nằm trần.
8. **Đọc `throttler.guard.js` cứu hai bug trước khi viết.** (a) `skipIf` của throttler có tên **thay thế** `skipIf` chung (`namedThrottler.skipIf || commonOptions.skipIf`) — không tự kiểm lại "rate limit đang tắt" thì toàn bộ e2e (đã tắt rate limit) vẫn bị đếm đăng nhập. (b) Throttler có tên đặt header `Retry-After-<tên>`, không phải `Retry-After` → ghi đè `throwThrottlingException`: đặt `Retry-After` chuẩn + ném `Errors.common.rateLimited()` (body chuẩn thay vì `ThrottlerException` trần). `getTracker` khi chưa đăng nhập gọi `super` để giữ `normalizeIp` (gom IPv6 theo subnet — xoay địa chỉ trong một /64 không thoát được).
9. **Thứ tự `APP_GUARD` = thứ tự trong mảng providers của CÙNG module.** Guard rate limit cần `req.user` → đăng ký ngay sau `JwtAuthGuard` trong `AuthModule`. Đột biến hoán đổi hai dòng → đúng 1 test đỏ (khoá theo người dùng: hai người cùng IP giành giới hạn của nhau). Env được đọc lúc `import` AppModule → file test muốn cấu hình khác dùng `vi.hoisted` (chạy trước mọi import, sau `setupFiles`); không thể có hai cấu hình trong một file → ca "không tin proxy" là file riêng. Hai đột biến **vô hiệu** đã bắt được khi đọc kết quả: chèn `skipIf` vào object bị khoá cùng tên phía sau ghi đè; `set('trust proxy', 0)` của Express = "tin 0 tầng" = không tin, tương đương code gốc. 6 đột biến thật (storage bộ nhớ, luôn khoá theo IP, credential chỉ theo IP, nới throttler `account`, hoán đổi thứ tự guard, luôn tin proxy) đều đỏ.
10. **Dữ liệu benchmark tự tương quan.** Lần chạy đầu: người xem "thưa" lọc `status=failed` trả 0 dòng. Seed chọn status theo `g % 10` và kênh theo `(g * 31) % 200 + 1` — `g` chia hết cho 10 thì kênh luôn rơi vào 1, 11, 21, … nên 7 kênh 194–200 không bao giờ có meeting `failed`. Số đo khi đó "đẹp" mà sai. Sửa: chọn bằng `random()` sau `setseed(0.42)` (vẫn lặp lại được). Benchmark đo ĐÚNG SQL của code (`dist/` + logger Drizzle bắt câu lệnh) chứ không chép tay câu SQL — chép tay sẽ lệch ngay khi code đổi.
11. **Planner không "biết" ý đồ của tập ứng viên — `IN (subquery)` vs `= ANY(ARRAY(subquery))`.** Bản đầu: `id IN (ứng viên) AND meetingVisibleTo(…)`. Planner ước lượng đi lùi `meetings_org_recorded_idx` + lọc bằng điều kiện xem (hashed SubPlan cũ) rẻ hơn → chạy đúng kế hoạch CŨ, phần ứng viên `never executed`; dày + lọc status 31 → 134 ms. `= ANY(ARRAY(…))` biến ứng viên thành InitPlan chạy MỘT lần trước, rồi tra PK theo mảng — planner hết đường đi lùi cả org. Kế đó: lọc lại bằng `meetingVisibleTo` từng dòng trên ~3 000 ứng viên vẫn ăn nửa thời gian của ca dày → bỏ lọc lại trong SQL, thay bằng **test đối chiếu** (oracle): mọi người xem × bộ lọc × duyệt hết trang so với chính `meetingVisibleTo` — định nghĩa vẫn ở một chỗ, chỉ cách THỰC THI tách ra (04 §3 ghi rõ ngoại lệ này). 6 đột biến (bỏ kiểm đã xoá, kênh chỉ công khai, bỏ luồng không chủ, bỏ luồng của mình, "một lượt" nhận share ở BẤT KỲ kênh, bỏ cursor ở luồng theo kênh) đều đỏ kèm số lệch cụ thể; ép luôn một hình dạng luồng "qua kênh" (cả hai chiều) vẫn xanh — hai hình dạng đều đúng, chỉ khác chi phí.
12. **Chọn kế hoạch bằng mô hình chi phí đơn giản: k² < K.** Theo từng kênh (`LATERAL`) đọc ≈ k·n/s dòng (k kênh thấy được, n trang, s tỉ lệ qua bộ lọc); một lượt theo thời gian + `EXISTS` share vào kênh thấy được đọc ≈ n·K/(s·k). So hai vế → theo từng kênh rẻ hơn khi k² < K. Đo xác nhận: dày (k = 150, K = 200) + lọc status theo từng kênh 59 ms → một lượt 0.68 ms; thưa (k = 7) thì theo từng kênh tốt hơn. Cần một câu nhỏ lấy id kênh thấy được + tổng số kênh trước (≈ 0.2 ms, đã tính trong bảng) — id đó dùng luôn làm tham số mảng (`sql.param(ids)` + `::uuid[]`; nhét mảng thẳng vào template Drizzle sẽ trải thành `($1, $2, …)`).
13. **JIT là bẫy của OLTP; benchmark phải đo đúng cấu hình pool của app.** Ca rỗng v2: 9 buffer mà 18 ms — `EXPLAIN` có khối `JIT: … Emission 15.1 ms`: ước lượng chi phí ~3M (> `jit_above_cost` 100k) → Postgres compile JIT cho một câu thực tế rất rẻ. Tắt ở `createPgPool` (`options: '-c jit=off'`); benchmark chuyển sang dùng chính `createPgPool` để mọi thiết lập pool (timeout, jit) được đo. Benchmark cũng phải đo MỌI câu của một lần gọi — đo câu cuối thì giấu mất câu lấy kênh.
14. **Bẫy nhỏ trên đường:** (a) Drizzle `select({ id: ms.meetingId })` — khoá `id` chỉ là tên field phía JS, SQL vẫn ra `"ms"."meeting_id"` → `s.id does not exist` trong `LATERAL`; cần ``sql`…`.as('id')``. (b) drizzle-kit sinh `ADD COLUMN … NOT NULL` không default → sửa tay migration thành thêm cột NULL → backfill → `SET NOT NULL`. Cột `NOT NULL` không default khiến typecheck chỉ ra MỌI chỗ insert share (repository, factory test) — riêng seed `.mjs` của benchmark không qua typecheck nên lỗi lúc chạy. (c) Test đối chiếu lần đầu "xanh" với 0 dòng so sánh: LCG `seed * 1103515245` vượt 2^53 → mất bit thấp → `% 4`, `% 8` luôn 0 → mọi meeting bị xoá, không share nào; assertion "đã so > 100 dòng" bắt được. (d) Xoá mềm meeting GIỮ dòng share → luồng qua kênh phải join `meetings` để loại meeting đã xoá.
15. **Thuộc tính role KHÔNG kế thừa — tách "nhóm" và "user đăng nhập".** `GRANT` trên bảng kế thừa qua membership, nhưng `LOGIN`, `BYPASSRLS`, `SUPERUSER` thì không. Nên: migration tạo nhóm `meetnote_app` / `meetnote_worker` (`NOLOGIN`, giữ GRANT + `ALTER DEFAULT PRIVILEGES`, không mật khẩu trong git); `provisionLoginRoles` tạo `meetnote_api_login` / `meetnote_worker_login` (mật khẩu từ env, `BYPASSRLS` đặt TRÊN user worker). `CREATE ROLE … PASSWORD` không nhận tham số bind → `escapeLiteral` của `pg`. Role là đối tượng của cả cluster → `CREATE ROLE` trong `DO $$ … IF NOT EXISTS`; GRANT là của từng database nhưng database test clone từ template nên mang theo.
16. **Toàn bộ e2e chạy dưới user api là bằng chứng GRANT ĐỦ (575/575); `app-roles.int-spec` chứng minh GRANT KHÔNG THỪA** (CREATE / DROP / ALTER TABLE, TRUNCATE, CREATE FUNCTION → `42501`). Một test cũ đổi nghĩa: `audit_logs` "UPDATE / DELETE / TRUNCATE bị trigger từ chối (23001)" — dưới user app, lệnh bị chặn ở lớp QUYỀN (`42501`) trước khi tới trigger → tách thành hai lớp, test riêng: user app → `42501` (`REVOKE UPDATE, DELETE` + không cấp TRUNCATE), chủ schema → `23001` (trigger vẫn giữ cả khi ai đó có quyền cao). 3 đột biến migration (bỏ default privileges, cấp thừa TRUNCATE, bỏ REVOKE audit) đều đỏ. Chạy thật trên DB dev có dữ liệu: migration `0010` backfill 4 share (0 dòng NULL), provision hai user, api / worker kết nối bằng user riêng (`pg_stat_activity` thấy `meetnote_api_login` / `meetnote_worker_login`), smoke fan-out M10 vẫn chạy.
